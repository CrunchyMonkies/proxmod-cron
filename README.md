# proxmod-cron

Cron management for Proxmox VE, as a [proxmod](../proxmod) extension.

A **Cron** tab in the datacenter view for cluster-wide entries, a **Cron** tab in
the node view for host entries, a read-only inventory of every *other* cron entry
on the host, per-run history with captured output, a REST API, and a documented
Perl and JavaScript API other extensions build on.

**This package is not standalone.** It is a proxmod extension and does nothing
without `proxmod (>= 0.2.0)` installed.

---

## What it actually does

Job definitions live in two JSON stores. A one-line anchor in `/etc/cron.d`
renders them into real cron files, and the system's own cron runs them.

```
        definitions                      materialisation              execution
  ┌───────────────────────────┐      ┌──────────────────────┐     ┌────────────┐
  │ /etc/pve/proxmod/cron.cfg │──┐   │ /etc/cron.d/         │     │            │
  │   (cluster, replicated)   │  ├──▶│   proxmod-cron       │────▶│  /usr/sbin │
  ├───────────────────────────┤  │   │     (anchor, conffile)     │    /cron   │
  │ /etc/proxmod/cron.cfg     │──┘   │   proxmod-cron-cluster     │            │
  │   (this node only)        │      │   proxmod-cron-node  │     └─────┬──────┘
  └───────────────────────────┘      └──────────────────────┘           │
                                                                        ▼
                                                      ┌───────────────────────────┐
                                                      │ proxmod-cron-exec         │
                                                      │   start / output / finish │
                                                      └─────────────┬─────────────┘
                                                                    ▼
                                                            ┌──────────────┐
                                                            │   journald   │
                                                            └──────────────┘
```

There is **no new daemon and no scheduler of its own**. The anchor,
`/etc/cron.d/proxmod-cron`, runs `proxmod-cron-sync` every minute; sync reads both
stores and rewrites the two generated files only when the rendered text differs.
That is what makes a cluster job created on node A appear on node B, and it is
why the package needs no `postinst` to bootstrap itself.

What an administrator sees with `cat /etc/cron.d/proxmod-cron-node` is what runs:

```
# Generated by proxmod-cron. Do not edit — changes are overwritten.
# Source: /etc/proxmod/cron.cfg   Node: pve1   Jobs: 2
SHELL=/bin/sh
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
MAILTO=""

# job: nightly-trim (command) — fstrim all mounts
30 2 * * *	root	/usr/lib/proxmod-cron/proxmod-cron-exec node nightly-trim -- /usr/sbin/fstrim -a
```

**Only `/etc/cron.d` is ever written**, and only the two files named above. User
crontabs under `/var/spool/cron/crontabs`, `/etc/crontab` and the `run-parts`
directories are read for the inventory view and never modified — not even to
disable an entry, because commenting out a line in a file another package owns
would be undone by that package's next upgrade.

## Installing

```sh
apt install ./proxmod-cron_0.1.0_all.deb
proxmod-verify          # exits 0 and lists 'cron' as loaded
```

Installing it writes `/usr/share/proxmod/extensions.d/50-proxmod-cron.conf`,
which fires proxmod's dpkg trigger and restarts `pvedaemon` and `pveproxy`.

`order: 40` in the manifest — below the default 50 — so an extension that
declares `"requires": ["cron"]` and sits at 50 loads after this one and finds
`ProxmodCron` already registered.

### Files

| Path | |
|---|---|
| `/usr/share/perl5/ProxmodCron{,.pm}` | backend modules |
| `/usr/share/proxmod/extensions.d/50-proxmod-cron.conf` | manifest |
| `/usr/share/proxmod/www/proxmod-cron.js` | frontend asset |
| `/usr/lib/proxmod-cron/proxmod-cron-{sync,exec}` | internal helpers |
| `/usr/sbin/proxmod-cronctl` | admin CLI |
| `/etc/cron.d/proxmod-cron` | **conffile:** the anchor line only |
| `/etc/cron.d/proxmod-cron-{cluster,node}` | generated — do not edit |
| `/etc/proxmod/cron.cfg` | node job definitions, mode `0600` |
| `/etc/pve/proxmod/cron.cfg` | cluster job definitions, replicated |
| `/var/lib/proxmod/cron/` | locks and the last-run cache — derived only |

`apt purge` removes the generated cron files, `/var/lib/proxmod/cron` and the
node store. It deliberately leaves `/etc/pve/proxmod/cron.cfg` alone — that is
cluster configuration, and purging one node must not delete the cluster's data —
and it leaves the journal entirely alone, because a package purge has no business
vacuuming the host's logs.

## Job definitions

```json
{
  "version": 1,
  "mailto": "",
  "jobs": {
    "nightly-trim": {
      "type": "command",
      "origin": "user",
      "enabled": true,
      "schedule": "30 2 * * *",
      "user": "root",
      "comment": "fstrim all mounts",
      "nodes": ["pve1", "pve2"],
      "track": true,
      "keep_output": true,
      "command": ["/usr/sbin/fstrim", "-a"]
    }
  }
}
```

| Field | |
|---|---|
| `type` | job type id; `command` is built in, others come from the plugin registry |
| `origin` | `user` or `extension` — **who may add and remove it** (see below) |
| `owner` | `origin: extension` only: the proxmod extension id that registered it |
| `enabled` | default `true`; a disabled job renders as a commented-out line, so it stays visible in the file |
| `schedule` | 5-field cron spec, or `@hourly` / `@daily` / `@weekly` / `@monthly` / `@yearly` / `@reboot` |
| `user` | crontab user field, default `root` |
| `nodes` | cluster store only — which nodes render this job; absent means every node |
| `track` | default `true`; wrap in `proxmod-cron-exec` so the run and its output are recorded |
| `keep_output` | default `true`; when `false`, only start and finish are recorded and the job's output is discarded |

**A command is an array, end to end.** No string is ever handed to a shell in
Perl; quoting happens once, in the renderer, for cron's benefit. `%` is escaped,
because in a crontab it means "newline, rest is stdin" and an unescaped one
silently truncates the job.

### Origin — who may change what

`origin` is a second axis of authority, orthogonal to permissions. Permissions
answer *may this user?*; origin answers *may anyone, through this surface?* An
action is offered only when both say yes, and both are enforced server-side.

| Origin | Add | Enable / disable | Edit | Remove |
|---|---|---|---|---|
| `user` — created by a person | ✔ | ✔ | ✔ | ✔ |
| `extension` — created by another extension | ✘ | **✔** | ✘ | ✘ |
| `extension`, owner uninstalled (*orphaned*) | ✘ | ✔ | ✘ | **✔** |
| foreign — another package's own cron file | ✘ | ✘ | ✘ | ✘ |

**A dynamically added entry is enable/disable only.** The extension that created
it owns its schedule, its command and its existence; an administrator owns
whether it runs. An administrator must always be able to stop a job without
uninstalling the package that created it, and without that decision being
quietly reverted on the next daemon restart.

An **orphan** — a job whose owning extension is no longer loaded — still renders
and still runs, and becomes removable. Otherwise uninstalling an extension would
leave permanently undeletable rows.

## Run tracking and output

Everything with `track: true` runs through `proxmod-cron-exec`, which records the
run and its output as **structured journald entries**:

```sh
journalctl -o json PROXMOD_CRON_JOB=nightly-trim       # everything about one job
journalctl -o json PROXMOD_CRON_RUN=1739…-a3f10b2c     # one run, output included
journalctl MESSAGE_ID=<finish> --since -30d            # every completion
```

Fields: `PROXMOD_CRON_JOB`, `_SCOPE`, `_TYPE`, `_RUN`, `_EVENT`
(`start`/`output`/`finish`/`skipped`/`change`), `_STREAM`, `_EXIT`, `_SIGNAL`,
`_DURATION_MS`, `_USER`, plus `PRIORITY` and a per-event-class `MESSAGE_ID`.

Because management actions are journalled with the same `PROXMOD_CRON_JOB` field,
one query answers the question that actually gets asked during an incident:
**who last changed this job, and how has it run since?**

Three properties worth knowing:

- **journald is the store of record.** `/var/lib/proxmod/cron/last-run.json` is
  a derived cache for the grid's status column. Delete it and nothing is lost but
  a `proxmod-cronctl reindex`.
- **Retention is the host's setting, not ours.** `SystemMaxUse`,
  `MaxRetentionSec` and `journalctl --vacuum-*` apply to these records the moment
  they exist. This package ships no journald configuration and no log store of
  its own. If `/var/log/journal` is absent, history dies at reboot —
  `proxmod-cronctl doctor` says so, and the UI shows the warning on the Runs
  region. Nothing about a job *running* depends on history existing.
- **`MAILTO=""` in the generated files is deliberate**, and it is only defensible
  because the output goes to journald instead. Set the store-level `mailto` key
  if you do want the mail. A job with `track: false` under an empty `MAILTO`
  discards its output entirely — `proxmod-cronctl doctor` warns about that,
  because it is almost always a mistake.

**Anything a job prints ends up in the journal**, readable by anyone holding
`Sys.Syslog` or a shell on the host — a wider audience than the API, and wider
than the root mailbox this output used to go to. Set `keep_output: false` for a
job that prints things that should not spread. The job editor says so next to the
tracking checkbox.

## Permissions

Everything is expressed in **existing PVE privileges on existing ACL paths**.
`PVE::AccessControl` builds its privilege list and its path allowlist at compile
time with no registration hook, so a privilege named `Cron.Modify` would require
monkey-patching Proxmox — which is exactly what proxmod exists to avoid.

| Action | Path | Privilege |
|---|---|---|
| Read cluster jobs, types, status | `/` | `Sys.Audit` |
| Create / edit / delete / enable / disable a cluster job | `/` | `Sys.Modify` |
| Read node jobs, inventory, status | `/nodes/{node}` | `Sys.Audit` |
| Create / edit / delete / enable / disable a node job | `/nodes/{node}` | `Sys.Modify` |
| Run a job now, force a sync | `/nodes/{node}` | `Sys.Modify`, or delegated |
| Read run history — when, how long, exit status | `/nodes/{node}` | `Sys.Audit`, or delegated |
| **Read a run's captured output** | `/nodes/{node}` | **`Sys.Syslog`**, or delegated |
| Read the whole `proxmod-cron` journal | `/nodes/{node}` | `Sys.Syslog` |
| Read the job-type catalogue | — | any authenticated user |

**Run metadata and run output are gated differently on purpose.** That a job ran
at 02:30 and exited 1 is operational status. What it *printed* is arbitrary text
a root command produced, and reading it here must not be a way around the
privilege PVE demands for the same bytes at `/nodes/{node}/journal`.

**Delegation** lets a VM owner manage a backup job for their own VM without
`Sys.Modify` on the node. A job type declares which object its jobs are *about*:

```perl
sub required_privs {
    my ($class, $cfg) = @_;
    return [["/vms/$cfg->{vmid}", ['VM.Backup']]];
}
```

Authorization is then `Sys.Modify` on the scope root **or** every declared
privilege on every declared path. Two structural rules hold it together:

1. **An empty `required_privs` means "not delegable."** The built-in `command`
   type declares none — a command job is arbitrary root execution and there is no
   ACL path that honestly describes it.
2. **The delegated surface is a separate subtree**, `delegated-jobs/`, which
   refuses any type with an empty `required_privs` as its first act. The loose
   gate is safe because the path structurally cannot create a command job.

Delegated writes additionally freeze `user`, `track` and `type` — each is a route
to more than the delegation granted — and check the **stored** config as well as
the submitted one, so a user with rights on `/vms/101` cannot re-point a job at
`/vms/202`.

`GET permissions` on either scope returns what the caller may actually do,
computed with the same helper the write methods enforce with. The UI **disables**
what is not permitted rather than hiding it, with a tooltip naming the missing
privilege — a user who cannot find a feature files a support ticket; a user who
sees why it is greyed out asks for the right role. None of that is a boundary:
the server checks every call regardless.

## `proxmod-cronctl`

What an administrator uses when the web interface is not reachable.

```
  list [--scope cluster|node]        every defined job, with its next run
  show <id> [--scope S]              one job in full, with its last run
  render [--scope S] [--diff]        what would be written to /etc/cron.d
  validate                           check both stores and every job in them
  run <id> [--scope S]               run a job now, exactly as cron would
  sync [--dry-run] [--wait]          render and write what changed
  runs <id> [--limit N] [--since T]  run history, newest first
  log <runid> [--follow]             one run's captured output
  inventory                          every cron entry on this host
  reindex                            rebuild the status cache from journald
  doctor                             check what silently breaks cron and logging
```

`doctor` is the one to run first when something is not firing: it checks journal
persistence and rate limits, `MAILTO` versus `track`, unreadable stores, and
plugin modules a store references but that will not load.

## For extension authors

See **[docs/extension-api.md](docs/extension-api.md)**. Four surfaces:

- **Job-type plugins** — a Perl class with a `build_command` that returns an
  argv, so the effective command stays readable in `/etc/cron.d`.
- **`ProxmodCron::Client`** — create and manage jobs from your backend. Jobs are
  stamped with your extension id, taken from your `Proxmod::API` object rather
  than from an argument.
- **The REST API** — `/cluster/proxmod/cron` and `/nodes/{node}/proxmod/cron`.
- **The `ProxmodCron` JS namespace** — contribute an editor form for your job
  type, or open the run-log window from your own panel.

## Development

```sh
make lint      # perl -c and -c -T on every module and script, node --check, manifest JSON
make test      # prove -r t/
make check     # both
make deb       # dpkg-buildpackage -us -uc -b
```

The test suite runs against a bare Debian with no Proxmox on it. That is a
property of the code, not a limitation of the tests: only `ProxmodCron::API2::*`
touches PVE at all, and `t/lib` stubs the parts of it those modules use.
Everything the cron side runs — the stores, the renderer, the spec parser, the
journal writer, the run wrapper — is PVE-free by design, because it is executed
from cron under a bare `perl`.

Run the suite as a **non-root** user. `PROXMOD_CRON_TEST_PREFIX`, which redirects
every path into a disposable tree, is honoured only when the effective UID is not
0 — so that the override cannot be turned against a production path as root.
